**Navigation background fix (2026-07-31):** the main nav and the journey pill originally used near-zero opacity + weak `blur(8px)` when unscrolled (copied from a pattern that suits homepage's dark hero image, not this page's plain-gradient hero with bold text right up against the nav) — resulting in visible text bleed-through, confirmed in a real screenshot. Fixed by raising `--nav-bg`/`--nav-bg-scrolled` to 0.88/0.95 opacity and strengthening blur to 24-28px, and giving the journey pill 0.98 opacity + its own `backdrop-filter` on a dedicated non-scrolling `.svc-journey-shell` wrapper (separate from the scrollable `.svc-journey-track`, cleaner separation of concerns). **Debugging pitfall to remember:** while chasing this, extensive pixel-level Playwright debugging (sampling raw PNG bytes) seemed to show "impossible" bleed-through even through a fully opaque background — this turned out to be a coordinate mistake: the sampled pixel was sitting directly on top of the legitimate gray `.svc-journey-item` label text (`#52525B` = exactly the RGB found), not behind the pill at all. Lesson: when a screenshot looks wrong, use `document.elementFromPoint()`/`elementsFromPoint()` at the *exact* suspect coordinate first to confirm what's actually painted there before assuming a rendering bug — don't eyeball zoomed crops and guess coordinates.

**Second correction (same day) — page-level section hierarchy.** The Journey Nav was originally placed right after the top `<Nav>`, always visible from page load. The correct Figma order (confirmed via a fuller page export, node `296:50`) is: Hero → "How We Build" (wrapped as a single-column soft "Story card," not the old 2-col sticky-head grid) → Bridge (a lightweight divider — line / label / line, then a plain centered note — not a bordered/gradient section) → the services tab bar (`.svc-journey`) → the 4 service blocks. The tab bar being `position: sticky` sitting *after* Bridge means it now starts in normal flow (invisible until scrolled to) and only sticks once it reaches the top — exactly "sticky when it reaches on top," achieved for free by relocating the JSX, no new CSS needed. **Bug this uncovered:** `moveGlide()`'s `item.scrollIntoView({block:'nearest', inline:'nearest'})` — meant only to keep the active pill visible within the *horizontally*-scrollable pill track on mobile — also walks up to the page/document as a scrollable ancestor. With the nav now positioned far down the page instead of right at the top, this caused the whole page to auto-scroll ~940px down on load. Fixed by replacing it with direct `track.scrollLeft` math instead of `scrollIntoView`. **Lesson:** `element.scrollIntoView()` (even with `block:'nearest'`) will scroll *every* scrollable ancestor including the page itself, not just the intended inner scroll container — for "keep visible within this specific inner scroller" behavior, set `scrollLeft`/`scrollTop` on that container directly instead.

**Critical gotcha found building this — `overflow: hidden`/`clip` on ANY ancestor breaks `position: sticky` descendants.** `.svc-block` had `overflow: hidden` (leftover from earlier scaffolding, likely for decorative clipping that no longer needed it). Once the new sticky `.svc-story-sticky` panel was nested inside it, sticky positioning worked near the top of the section but broke completely deeper in (element would report `position: sticky` in computed style yet render at wildly wrong coordinates, e.g. `top: -788px`, with `opacity: 0` from a `.reveal` class that appeared to un-trigger). Root cause: any ancestor between a sticky element and the true page scroll container with a non-`visible` overflow value breaks/constrains sticky's positioning range — even though it "looks fine" at first glance since the bug only manifests once you scroll far enough that the sticky element's containing-block math goes wrong. **How to apply:** before adding any new `position: sticky` element on this page, check every ancestor up to `.services-page` for `overflow` values other than `visible` (`grep overflow src/app/services.css`) — this is also why the earlier `.svc-block-visual` sticky trick this session specifically needed CSS **Grid** with `align-items: start` (not `flex`) to get the "room to travel" behavior; flex containers don't give a sticky child the same extra travel range that a grid track does.

**AI-Native wheel illustration: trimmed top/bottom whitespace (2026-08-03):** `AIWhatWeDoIllustration`'s `<svg viewBox>` had a lot of baked-in empty margin above/below the ring (measured via `getBBox()`: content occupied y 63.8→355 of a 0-400 viewBox, i.e. ~27% dead space top+bottom) — this showed up as a visibly tall `.svc-story-illustration` card with big gaps above "Plan" and below "Monitor." Fixed by cropping the viewBox from `"0 0 420 400"` to `"0 46 420 327"` — width/x untouched, so the horizontal scale factor (and therefore every node's rendered pixel size, font size, circle radius, etc.) is unchanged; only the vertical crop window shrank, which drops the rendered card height from ~396px to ~324px for free (browser computes `height: auto` from the new, boxier aspect ratio at the same CSS width). This is the general technique to reach for if a future illustration's card looks too tall/padded: measure `svg.getBBox()` vs `viewBox`, then crop viewBox y/height (not the elements) to trim dead space without touching any element's absolute coordinates or text size. Scoped to this one illustration only — the shared `.svc-story-illustration` box CSS (min-height 280px, etc.) was intentionally left untouched since the other 3 services' illustrations were already hitting that floor correctly.
